# Этап 9 — производительность и стабильность

Проверка от 2026-09-17. Статус: завершён в согласованных эмуляторных границах.
Контракт: [stage9-plan.md](stage9-plan.md). Runtime-проверки и профили ниже
выполнены на **0.8.1 / 9**; после завершения этапа версия поднята до
**0.9 / 10** по запросу пользователя. Исторические замеры не переименованы.
Физические телефоны/Fold исключены пользователем; ниже только эмуляторы.

## Изменения

- Исправлен реальный crash импорта FB2 на API 26: `MutableList.removeLast()` /
  `removeFirst()` из JVM-модуля связывались с новыми методами Java `List` при
  сборке на JDK 21. Используются совместимые `removeAt`; для всех трёх чистых
  JVM-модулей ограничен доступный JDK API через `-Xjdk-release=17`.
- `benchmark` теперь измеряет недебажную profileable сборку в отдельном процессе,
  импортирует свой FB2 и ждёт готовый текст/номер/доступность перелистывания.
  По пять повторений cold startup, single и spread; каждый проход листания
  содержит шесть настоящих жестов вперёд и шесть назад с проверкой номера.
- Добавлен UI stress: 100 перелистываний, шесть посещений примечания, два reflow
  со сменой размера шрифта/раскладки и два background/resume. Проверяются точные
  checkpoints, неизменность прогресса в примечаниях, cache/raster budgets.
- Нативный stress проверяет вытеснение bitmap, 120 повторных запросов готового
  окна без новой растеризации, trim до закреплённых соседей и освобождение
  владения поверхностями после `PaginationSession.close()`.
- Диагностический счётчик растеризаций читает живой кэш, а не замороженный снимок
  страницы во время curl.
- Добавлены отмена заблокированного копирования, отмена на границе публикации,
  восстановление после незавершённого удаления, исчезнувшего файла и `.part`/
  orphan-cover. Проверяется сохранность остальных книг, прогресса и закладок.
- Двухфазный тест сохраняет checkpoint, закладку, настройки и выбранную книгу,
  затем отдельный запуск после force-stop проверяет новый PID и чтение с диска.
  Fixture помечен собственным AtomicFile; очистка не удаляет посторонние книги.
- Настроены необязательная внешняя release-подпись и CI API 26/36; артефакты CI
  включают APK/AAB и отчёты. Версия/ключ публикации не менялись.
- Старый `PaperControlsFlowTest` изолирован от случайной открытой книги: свой
  FB2 с тремя главами, прокрутка действий в видимую область и ожидание завершения
  curl. Проверяется одновременно сохранённое место и реальный лист оглавления.

## Функциональные проверки и сборки

- Общий host gate: debug/release/benchmark APK, release AAB, JVM-тесты, lint и
  screenshot validation — успешно. 263 JVM cases и 120 screenshot cases;
  эталоны не перезаписывались. Финальный gate после отмены экспериментального
  изменения рендера: `BUILD SUCCESSFUL in 1m 47s`, 881 tasks
  (56 выполнены, 825 up-to-date). Неизменённые результаты Gradle переиспользованы.
- API 26, Pixel 2, 1080×1920 / 420 dpi: 12 storage, 5 database, 38 native
  reader tests; 5 parser smoke, library flow, paper controls и reader stress — успешно.
- API 36, Pixel 7, 1080×2400 / 420 dpi: 12 storage, 5 database и 38 native
  reader tests — успешно. Полный app-прогон: 45 случаев (два process-restart
  намеренно пропущены), единственный сбой — старый `PaperControlsFlowTest`;
  исправленная версия прошла отдельным повтором после `LibraryFlowTest`
  (2/2). Таким образом, проверены все 43 исполняемых случая; весь набор повторно
  одной командой после исправления теста не запускался.
- Финальный двухфазный process-restart на API 26: три последовательных прохода
  prepare → новый PID → verify. Проверяется чтение настроек до создания controller.
  Начальная версия теста использовала дополнительный холодный DataStore collector
  во время записи и нестабильно получала старое значение. Теперь синхронизация
  идёт через постоянного наблюдателя controller, а новый процесс независимо
  проверяет диск; sleep/retry и ослабления проверок нет.
- API 36: такой же process-restart прошёл трижды; native/UI stress завершены
  в обеих раскладках (`completedModes=2`).
- Release APK подписан существующим локальным **тестовым** Android-ключом;
  `apksigner verify` проходит. AAB проверен `jarsigner`. Это проверка механизма
  внешней подписи, не готовая подпись для публикации в магазине. На API 26 и 36
  установлен release APK, проверено открытие готового текста книги; в package
  flags отсутствует `DEBUGGABLE` (`api26-release-ready.png`,
  `api36-release-ready.png`). Итоговый crash-buffer API 36 пуст.

## Профилирование

Конфигурация: API 36 / x86_64 Google APIs, Pixel 7, 1080×2400, 420 dpi,
KVM, `-gpu swangle`. Версия 0.8.1 / 9, недебажный profileable `benchmark`.
Для листания — `CompilationMode.Full`, для холодного старта — `None`.
Подавлено только предупреждение `EMULATOR`; анимации включены.

Завершённый spread baseline: пять проходов по 12 жестов (шесть вперёд,
шесть назад, 24 шага на жест). `frameDurationCpuMs` P50 **589,3 мс**,
P95 **666,8 мс**, P99 **791,8 мс**; `frameOverrunMs` P50 **857,7 мс**,
P95 **1 011,7 мс**. Это очень медленный эмуляторный рендер, не результат
«60 FPS». Холодный старт: пять запусков, initial display min **1 140,4 мс**,
median **1 337,2 мс**, max **2 203,1 мс**. Это первый кадр Activity,
не время полной готовности текста: готовность отдельно проверяется сценарием,
а приложение не публикует `reportFullyDrawn`.

Финальный single-прогон с исправленным setup: **5/5** проходов, те же
12 жестов и строгий возврат на исходную страницу. `frameDurationCpuMs`
P50 **1 147,8 мс**, P95 **1 585,9 мс**, P99 **1 665,8 мс**;
`frameOverrunMs` P50 **1 693,6 мс**, P95 **2 377,2 мс**.
Медиана — 334 кадра на проход. Подтверждение: `macro-single-final/`,
`macrobenchmark-single-final.txt` (`OK (1 test)`, пять trace-файлов).
Это отдельный завершённый прогон после исправления harness; сравнение single
и spread здесь не является A/B-измерением изменения кода рендерера.

Разобрана первая spread-трасса (`spread-iteration0.perfetto-trace`):

- `measureBlock` 102,07 с; RenderThread — 99,42 с scheduled CPU, main — 1,34 с.
- 300 синхронных input events занимают 80,48 с; `waitForIdle` внутри измеряемого
  блока отсутствует. Жесты ждут рендер, а не фиксированный десятисекундный timeout.
- Фоновая `Listai.pageRaster`: 16 операций, 232,75 мс суммарно; на main — ноль.
- Skia `FillRectOp` занимает 87,49 с включённого времени, но сама метка не
  доказывает, что это вычисления Kotlin/Compose или конкретного painter.

Отдельный 40-секундный Simpleperf-capture на готовой странице содержит шесть
жестов (три вперёд/три назад), 15 147 samples, потерянных samples — ноль.
91,48% self samples приходятся на `libc.read` в RenderThread;
`QemuPipeStream::commitBufferAndReadFully` — 93,79% inclusive. В этом окружении
основной подтверждённый CPU-путь — обмен с эмулируемым графическим драйвером.
Это не основание переписывать пагинацию или утверждать такую же задержку
на пользовательском устройстве. Проценты относятся к одному CPU-capture,
не ко времени всей пользовательской операции; cold startup перед ним сбросил AOT.

Проверенная гипотеза — ограничить две прозрачные градиентные заливки бумаги
узкими полосами. Она отклонена: три существующих curl-эталона изменились
на 1–2 пикселя / один уровень RGB. Изменение отрисовки отменено, эталоны
не обновлялись; ускорение от этой гипотезы не заявляется.

Сохранены Perfetto + SQL-разбор, исходный `curl-perf.data`, self/inclusive/CSV
Simpleperf-отчёты и macrobenchmark JSON. В первой Perfetto-трассе есть пять
`sorter_push_event_out_of_order`; точный порядок пограничных событий требует
осторожности, многосекундные итоги согласуются с CPU-capture.
Команды повторения — в [benchmark/README.md](../benchmark/README.md).

Первый single benchmark обнаружил ошибку самого harness: после смены ориентации
он успевал начать измерение ещё в spread и получал +2 вместо +1. Setup теперь
проверяет фактическое соотношение сторон, число опубликованных листов и два
одинаковых готовых снимка; используются абсолютные natural/left rotations.
Строгая проверка +1/+2 не ослаблена.
