# Версия 1.2 — план выполнения с субагентами

Статус: пакеты реализации и итоговые проверки завершены; локальный подписанный
кандидат `1.2-rc1` / 16 подготовлен для пользователя. Источник требований: [v1.2-plan.md](v1.2-plan.md).
Результаты и артефакты: [v1.2-verification.md](v1.2-verification.md).

Пользователь после утверждения плана поручил запустить субагентов, оформить
каждое логическое изменение отдельным Git-коммитом и выдать подписанный APK.
**Push, теги и публикация не разрешены и не выполнялись.**

Работа шла в общем checkout с четырьмя активными участниками: root отвечал
за контракты, интеграцию, Git и все Gradle/AVD-проверки; A — данные, миграции
и кота; B — библиотеку и жесты; C — парсеры, пагинацию и ридер. Одновременное
редактирование одного файла исключалось передачей владения. Каждый пакет
принимался root и фиксировался отдельным локальным коммитом.

Ниже сохранён исходный план как перечень контрактов, зависимостей и обязательных
проверок. Его формулировки будущего времени описывают порядок выполнения;
фактический итог вынесен в отчёт, чтобы не смешивать намерения с доказательствами.

## Организация и ограничения

- Не более **четырёх одновременно работающих агентов: root + три субагента**.
  Это субзадачи одной работы, без создания отдельных пользовательских задач.
- Root координирует контракты, интеграцию и проверки; субагенты владеют
  ограниченными пакетами. Библиотека и ридер разрабатываются параллельно.
- Один файл имеет одного активного владельца. В общем checkout запрещены
  независимые правки одного файла, откат чужой работы и массовый reformat.
  Передача файла другому владельцу фиксируется сообщением с текущим состоянием.
- Перед стартом проверить `git status` и сохранить уже подготовленные документы
  и референсы как часть текущей работы. Не стирать существующие изменения.
- Изолированные worktree нужны только при реальной необходимости; они
  не заменяют согласование API и не копируют незакоммиченные изменения сами.
- Зависимости между пакетами передаются небольшими завершёнными изменениями
  с перечнем затронутых файлов и проверок. Несовместимые API не меняются молча.
- Базовые навыки: [listai-books](../.agents/skills/listai-books/SKILL.md)
  и [listai-reader-ui](../.agents/skills/listai-reader-ui/SKILL.md).
  Для будущих прогонов эмулятора/профилирования использовать доступные
  `android-emulator-qa` / `android-performance` по необходимости.
- Исходный план не разрешал выпуск. Последующий запрос пользователя разрешил
  реализацию и локальный подписанный APK: версия изменена с 1.1 / 15 на
  1.2-rc1 / 16. Push, теги и публикация по-прежнему запрещены.

## Исходное состояние кода на старте

| Область | Факт и следствие для работ |
| --- | --- |
| База | `LibraryDatabase.kt` имеет схему **4**. Нужна одна общая миграция **4→5** для стопок/метаданных/нового состояния чтения, плюс цепочки 1/2/3→5. Историческое упоминание v3 в навыке не является текущей схемой. |
| Метаданные | `BookMetadata` уже знает список авторов, жанры и серию; `LibraryBook`/`BookEntity` их полностью не сохраняют. FB2 читает серию/жанры, EPUB читает жанры, PDF имеет ограниченные метаданные. Для picker нужен сохранённый индекс и дообогащение старых книг. |
| Ввод библиотеки | `LibraryScreen.kt` объединяет long-press, drag/reorder, отпускание и автопрокрутку. Поиск, pinch, стопки и кот должны подключаться через одного владельца ввода. |
| Средний масштаб | Текущие расчёты: шаг колонок 164 dp, предел ширины книги 154 dp, отношение высоты 1.48, промежутки 24 dp. Уровень MEDIUM сохраняет текущую геометрию с её ограничениями окна. |
| Начала глав | `BookBlock.Heading` не отличает главу от подзаголовка; многоабзацный FB2 `title` даёт несколько Heading. Нужна семантическая проекция, сохраняющая IDs/UTF-16 offsets. |
| Пагинация | Главы затрагивают `IncrementalPaginationEngine.kt` и отдельную ветку `FootnotePagination.kt`. Нельзя исправить только книги без сносок. |
| Служебные страницы | `PaginatedBookState.kt` использует специальные индексы для аннотации/TOC. Описание на бумаге Fold и отдельный титул меняют навигацию, restore и сцены curl. |
| Жизненный цикл | `ListaiApp.kt` сохраняет библиотеку в композиции под ридером. Коту требуется явный признак активности; скрытие UI не гарантирует остановку анимации. |
| Проверки библиотеки | Живые UI-тесты находятся в `:app`. У `:feature:library` есть JVM/screenshot-тесты, но пока нет instrumentation runner. |

## Этап 0. Общий контракт до параллельных правок

**Владелец: root.** Подготовительный этап будущей реализации.

1. Зафиксировать текущие fixtures/поведение среднего масштаба и восстановление
   базы 1.1. Не заменять существующие goldens до появления намеренных изменений.
2. Определить нейтральные типы и операции библиотеки:
   - глобальный каталог всех книг независимо от видимости на полке;
   - устойчивый ID стопки, смешанный элемент полки «книга / стопка»;
   - порядок общей полки и отдельный порядок внутри стопки;
   - навигационный контекст root/stack/search и anchor видимого предмета;
   - команды create/rename/add/extract/move/reorder/dissolve и структурный Undo;
   - состояния доступности метаданных и события фонового дообогащения.
3. Определить контракт ридера:
   - последовательность **обложка → описание → титул → текст**;
   - отдельная позиция титула при сохранении source/annotation/TOC/note anchors;
   - семантика главы, связанный диапазон исходного заголовка и номер;
   - проекция явно обозначенного исходного титула без удаления source-блоков;
   - оглавление как отдельный переход/возврат, без вставки в выбранную цепочку;
   - FB2/EPUB используют новый контракт, `FixedPage` PDF остаётся неизменным.
4. Согласовать общие настройки: `showClock = true`, три уровня масштаба
   с MEDIUM по умолчанию; один DataStore и прежние настройки сохраняются.
5. Определить единый приоритет ввода: активный modal/search → мультитач/отмена
   незавершённого drag → scroll или pull-search → long-press/drag → обычный tap.
   Подтверждённые пустые taps передаются коту отдельными событиями.
6. Опубликовать DTO/callbacks и fixtures, достаточные для независимой сборки UI.
   Точные имена типов выбираются здесь, до одновременных правок потребителей.
   Требования к поведению не откладываются на этот этап: они уже зафиксированы
   в [требованиях](v1.2-plan.md).

**Выход G0:** все три субагента знают один контракт и границы файлов; нет двух
претендентов на `LibraryModels.kt`, `AppPreferences.kt` или схему Room.
Подготовительные изменения собираются, существующие модельные проверки проходят.

### A / D1. Данные и сохранность

**Владение:** `core/model/LibraryModels.kt`, библиотечные новые типы в `core/model`,
`ReaderPreferences.kt`, `core/database/`, `core/files/LibraryRepository.kt`
и новые helpers метаданных/структурных операций. Остальной импорт не переписывать.

- Ввести смешанный порядок полки, стопки и членство с ограничением одной позиции
  на книгу. Каждая составная операция публикуется одной транзакцией.
- Подготовить **единственную** схему v5 и миграцию 4→5, сохранив все старые
  migrations, файлы, BookId, shelf order, progress, annotation/TOC и bookmarks.
  Новый reader checkpoint приходит из G0, а не отдельной конкурирующей миграцией.
- При импорте сохранять структурированные метаданные. Старые частные копии
  обрабатывать в фоне ограниченными порциями, с версией проекции и возможностью
  продолжить после прерывания. Парсинг не выполняется внутри SQL migration,
  UI composition или синхронного старта библиотеки.
- Отсутствие серии/жанра считать нормальным состоянием. Не перечитывать такую
  книгу бесконечно. Ошибка одного исходника не блокирует остальные книги.
- Реализовать структурную отмену без снимка всего BookEntity: свежие checkpoint,
  закладки и импорт не должны откатываться. Проверить гонки удаления/импорта.
- Добавить clock/zoom preferences с сохранением ранее установленных значений.

**Сдача:** операции и наблюдаемые состояния работают без UI; целевые проверки
покрывают membership/order/undo, обновление 1.1, close/reopen, backfill interruption.
После сдачи D1 агент A освобождается для пакета E1 с котом.

### C / R1. Источник, страницы и часы

**Владение:** `core/model/BookDocument.kt` и новые нейтральные chapter-типы,
`format/fb2/`, `format/epub/`, `reader/pagination/`, `feature/reader/`,
новый векторный орнамент в `core/designsystem/` и относящиеся тесты/строки.
**Исключения:** `ReaderDemoScreen.kt` у root; `LibraryModels.kt`,

Последовательность внутри пакета:

1. Source semantics FB2/EPUB: объединённый заголовок главы, номер/название,
   вложенность и явный исходный титул без смены стабильных source IDs/offsets.
   При необходимости читать поддерживаемые metadata серии EPUB, не выдумывать их.
2. Пагинация: начало главы с новой страницы в обеих ветках, предотвращение

3. Служебная навигация: белое описание в SINGLE/SPREAD, отдельный титул,

4. Поверхности: общий векторный орнамент, переносы длинного текста, cache keys,

## Волна 3. Независимое ревью и общая приёмка

- Освободившийся автор данных проверяет reader anchors/restore, автор reader
  проверяет сохранность стопок/Undo, автор библиотеки — общие переходы
  и конфликтующие жесты. Ревью read-only, исправляет владелец файлов.
- Root проверяет миграции, интеграцию, визуальные результаты, движение обложки
  и отсутствие фоновой работы невидимых компонентов.
- После осмотра actual/diff обновляются только намеренно изменённые screenshot
  эталоны. Imagegen-концепты и фото кота не становятся golden-файлами.
- После исправлений выполнить G3 ниже и оформить `docs/v1.2-verification.md`
  с фактическими результатами A1–A11, командами, артефактами и ограничениями.

## Проверки и распределение ресурсов

**Один владелец Gradle на общем checkout — root.** Агенты передают команды
и запрос на запуск; общий Gradle/KSP/schema generation, screenshot update
и verification не запускаются одновременно разными агентами. Во время проверки
затронутый пакет не редактируется. Нельзя обобщать зелёный результат одного
снимка checkout на файлы, которые после этого были изменены.

**Один владелец конкретного AVD.** Для каждого запуска фиксировать serial/API,
размер, density, язык, тему и backend. Не выполнять одновременно install,
force-stop, fold/rotate или instrumentation на одном устройстве. Параллельные
AVD возможны только при независимых serial и достаточных ресурсах.

### Focused проверки

После модельных/логических изменений:

```bash
./gradlew :core:model:test :format:fb2:test :format:epub:test \
  :reader:pagination:test :reader:rendering:test \
  :feature:library:testDebugUnitTest :feature:reader:testDebugUnitTest \
  :core:files:testDebugUnitTest :core:database:testDebugUnitTest
```

Сборка затронутой instrumentation и screenshot validation:

```bash
./gradlew :core:database:assembleDebugAndroidTest \
  :core:files:assembleDebugAndroidTest :feature:reader:assembleDebugAndroidTest \
  :app:assembleDebugAndroidTest
./gradlew :feature:reader:validateDebugScreenshotTest \
  :feature:library:validateDebugScreenshotTest
```

На выбранном AVD API 26, затем API 36 — затронутые сценарии соответствующих
модулей, с runner class-фильтрами при целевых прогонах:

```bash
./gradlew :core:database:connectedDebugAndroidTest \
  :core:files:connectedDebugAndroidTest \
  :feature:reader:connectedDebugAndroidTest :app:connectedDebugAndroidTest
```

При подготовке исходного плана сборки не запускались. Фактические команды,
фильтры instrumentation и результаты выполнения перечислены в отчёте проверки.
Не планировать `:feature:library:connectedDebugAndroidTest` как существующий gate.

Не нужно перемножать каждый функциональный тест на все варианты внешнего вида.
Логику проверять целевыми сценариями, вёрстку — screenshot-матрицей. Широкое
окно на API 26 не выдавать за проверку реального hinge/posture-события.

Для повторного использования подходят существующие `LibraryLayoutTest`,
`LibraryReorderTest`, `V11LibraryUiTest`, `ShelfInteractionTest`,
`V11ShelfMigrationTest`, `ReaderPreferencesTest`, `LibraryRepositoryTest`,
`PhysicalAnnotationTest`, `AndroidPaginationTest`, `FixedPageSurfaceTest`,
`ReaderSessionRestorationTest` и `Stage9PersistenceTest`.

Проверки производительности целевые: одинаковый AVD/backend до и после,
нет layout/decode на кадрах curl, bounded cache, нет минутной репагинации
или кадровой петли спящего/скрытого кота. Если найдена проблема, собрать
gfxinfo/Perfetto/Compose evidence; не обещать FPS физических устройств.

### G3. Общий gate и завершение

```bash
./gradlew test lintRelease :app:assembleDebug \
  :feature:reader:validateDebugScreenshotTest \
  :feature:library:validateDebugScreenshotTest
```

- Полный host gate проходит на итоговом наборе изменений.
- Затронутые storage/UI-сценарии подтверждены на API 26 и 36, Fold отдельно.
- Намеренные визуальные изменения осмотрены; A1–A11 подтверждены evidence.
- Неисправная среда эмулятора описывается как ограничение, а не как пройденный
  сценарий. Непроверенный обязательный критерий не позволяет объявить приёмку
  завершённой. Физические устройства остаются вне текущего плана.
- Документация фактической архитектуры и отчёт согласованы с реализацией.
  Пользователь получает итог и ограничения; публикация выполняется отдельно.

## Критический путь

**G0 → D1 (данные/метаданные/миграция) → L1/I1 (реальные стопки и возвраты)
→ интеграционные миграции/Fold → G3.**

Независимая длинная ветка: **G0 → R1 (chapter semantics → обе пагинации
→ служебные страницы/anchors/curl) → визуальная приёмка → G3**.

E1 начинается после D1 и готового контракта опор от B, параллельно доводке
библиотеки и reader. Финальная приёмка ждёт все восемь функций. Временные
оценки без измерения этих веток не фиксируются; прогресс отмечается сдачей
конкретных пакетов и gates, а не числом запущенных агентов.
